# QADAM — бэкенд

REST API для сайта: Node.js + TypeScript + Express 5, база SQLite через встроенный модуль `node:sqlite`
(нужен **Node 22.13+**, нативных зависимостей и отдельного сервера БД нет).

Обычно запускается из корня репозитория вместе с фронтендом: `npm run dev` (см. корневой README).
Отдельно — из этой папки:

```bash
npm run dev        # http://localhost:3001, перезапуск при изменениях (tsx watch)
npm run seed       # демо-данные только для отдельной тестовой БД; защищённый reset отклоняется
npm run build      # tsc → dist/
npm start          # node dist/index.js (+ раздаёт ../frontend/dist, если он собран)
npm run typecheck
npm test           # интеграционные тесты API с отдельной временной SQLite, без сетевого сервера
```

## Настройки

Скопируй `.env.example` в `.env` (необязательно — у всех значений есть дефолты).

| Переменная | По умолчанию | Что это |
|---|---|---|
| `PORT` | `3001` | Порт API |
| `DB_PATH` | `./data/qadam.db` | Файл SQLite (относительно `backend/`). Создаётся сам; автозаполнение пустой БД зависит от `SEED_DEMO_DATA` |
| `NODE_ENV` | — | При `production` Campus demo запрещено независимо от `ALLOW_DEMO_LOGIN`; обычный seed demo и автосид выключены по умолчанию |
| `ALLOW_DEMO_LOGIN` | `true` в dev, `false` в production | Разрешить обычный seed demo (в том числе явным `true` в production); Campus demo доступно только вне production |
| `SEED_DEMO_DATA` | `true` в dev, `false` в production | Автоматически заполнить пустую БД демо-данными |
| `COOKIE_SECURE` | `false` в dev, `true` в production | Cookie сессии только по HTTPS. Для локальной проверки production через HTTP явно укажите `false` |
| `BILLING_MODE` | `preview` | Бесплатный пилот с показом цен. Только точное `enforced` включает проверку квоты/Campus и отказ при необходимости оплаты; платёжный провайдер не включается |

`NODE_ENV=production` не меняет режим биллинга автоматически: без явного `BILLING_MODE=enforced` публикации остаются бесплатными.

## Демо-данные

`src/seed-data.ts` — пользователи, публикации, проекты, чаты из макета. Email и пароль демо-аккаунтов
указаны там же (`DEMO_EMAIL`, `DEMO_PASSWORD`). Для новой демонстрации выбери отдельный `DB_PATH`, затем выполни `npm run seed`. Рабочую БД и её каталог не удалять.

`NODE_ENV=production` выключает автосид по умолчанию, но явный `SEED_DEMO_DATA=true` по-прежнему включает заполнение пустой БД. Явная команда `npm run seed` разрушительна для незащищённой тестовой БД. При наличии истории `publication_requests`, биллинга или Campus сброс отклоняется до удаления записей. Эта защита сохраняет также историю публикаций из выпуска с отключёнными тарифами. Campus demo проверяется отдельно и в production запрещено даже с `ALLOW_DEMO_LOGIN=true`; обычный `/demo` допускает этот явный override.

Эти настройки не удаляют уже созданные аккаунты. При выключенном демо обычный `/login` также блокирует известные seed email с публичным паролем. Настоящий аккаунт с тем же email и изменённым паролем остаётся доступным. Уже выданные cookie обычных seed-аккаунтов этим флагом не отзываются: автоматический запрет существующей сессии ниже относится только к новым Campus registry-аккаунтам. Для развёртывания используйте отдельную чистую БД без публичных тестовых паролей.

### Отдельный кабинет «ЕНУ · демо»

`POST /api/auth/campus-demo` создаёт при необходимости отдельный демонстрационный Campus и входит в его общий административный аккаунт. Это явный bootstrap, независимый от первоначального `seed`: нет назначения прав на реальный ЕНУ по названию, email или профессии текущего пользователя. Повторный вход использует тот же fixture и сохраняет изменения статусов, модерации и пакетов; не сбрасывает БД и не импортирует личные публикации. Демонстрация общая для посетителей, а не отдельная копия на браузер.

Изоляция действует на границе Campus tenant: обычным пользователям демо-вуз не предлагается для заявки, прямой `/campus/enroll` в него запрещён; registry-аккаунт не получает роль или студенческую принадлежность реального вуза. Это не отдельный экземпляр всей платформы: общие карта, публикации и другие функции QADAM остаются в том же приложении. Демонстрационные публикации и пользователи помечены `DEMO`.

Служебные таблицы `campus_demo_registry`, `campus_demo_identities`, `campus_demo_objects` фиксируют принадлежность демонстрационного tenant, аккаунтов и объектов. Их маркеры не переписываются при повторе. Демо-аккаунты не имеют пароля обычного входа. При выключении демо либо переходе в production уже выданная сессия любого из пяти registry-аккаунтов больше не авторизует запросы; это проверяется при чтении cookie, а не только на странице входа. Обычные реальные аккаунты и их Campus-роли от переключения настройки не меняются.

`GET /api/auth/options` сообщает доступность демо без создания fixture. Даже после успешного ответа options каждый POST снова применяет серверный gate. Полный сценарий проверки, включая конфликт существующих записей и сохранённую cookie после restart, — в [docs/demo-qa.md](../docs/demo-qa.md).

## Устройство

```
src/
├── index.ts          # старт: сид при пустой базе + listen
├── app.ts            # Express: middleware, роуты, обработка ошибок, раздача фронтенда
├── config.ts         # переменные окружения (+ загрузка backend/.env)
├── db.ts             # подключение SQLite, схема (CREATE TABLE IF NOT EXISTS), хелперы all/get/run/tx
├── auth.ts           # scrypt-хэши паролей, сессии в httpOnly-cookie, requireAuth
├── models.ts         # строки БД → JSON для фронтенда
├── billing.ts        # серверный месяц, подтверждения, расчёт, gate и история использования
├── publication-requests.ts # единая транзакция создания и совместимые повторы двух выпусков
├── campus.ts         # роли вуза, членство, opt-in публикации, видимость и аудит
├── campus-overview.ts # реальные агрегаты активности выбранного Campus
├── campus-demo-policy.ts # доступность и изоляция демонстрационного tenant
├── campus-demo.ts     # явный bootstrap и проверка владения неизменяемым fixture
├── seed.ts           # заполнение базы
├── seed-data.ts      # демо-контент
└── routes/           # auth, opportunities, conversations, users (+ projects), billing, campus
```

- **Авторизация:** cookie `qadam_session` (httpOnly, SameSite=Lax), в базе хранится только SHA-256 токена. Сессия живёт 30 дней.
- **Пароли:** вход и регистрация используют асинхронный scrypt. Синхронный helper оставлен для явной загрузки демо-данных.
- **Попытки входа:** `/register`, `/login`, `/demo`, `/campus-demo` вместе допускают 30 запросов с IP за 15 минут и 10 с одной парой IP/email.
  При превышении — `429 { error, retryAfter }` и заголовок `Retry-After` в секундах. Ограничитель работает в памяти
  одного процесса; для нескольких экземпляров нужен общий счётчик. IP берётся из Express без доверия произвольному `X-Forwarded-For`.
- **Валидация:** zod; ошибка — `400 { error, issues }`. Не вошёл — `401`, нет прав — `403`, не найдено — `404`.
- **Схема** создаётся при старте. Версионируемого мигратора пока нет; совместимые изменения схемы добавляются в `db.ts`. Таблицы биллинга создаются без сброса существующей БД; при инициализации приложения выполняется идемпотентный учёт старых публикаций. `npm run seed` нельзя использовать для восстановления рабочего приложения: защищённые данные блокируют сброс; для тестовой демонстрации нужен отдельный `DB_PATH`.

## API

Все ответы — JSON. 🔒 — нужен вход.

### Авторизация `/api/auth`

| Метод | Путь | Тело | Ответ |
|---|---|---|---|
| POST | `/register` | `{ name, email, password, city? }` | `{ user }` + cookie |
| POST | `/login` | `{ email, password }` | `{ user }` + cookie |
| GET | `/options` | — | `{ demoLogin, campusDemoLogin }`; публичные boolean-возможности, `Cache-Control: no-store`, без bootstrap; ordinary demo также требует существующий seed-аккаунт |
| POST | `/demo` | — | `{ user }` + cookie; обычный seed demo при разрешённом `ALLOW_DEMO_LOGIN` и существующем аккаунте; если аккаунта нет — 503 без сброса БД |
| POST | `/campus-demo` | `{}` или без тела | `{ user, campus: { id, name, city, isDemo: true } }` + cookie; вход в отдельный «ЕНУ · демо», произвольные поля тела отклоняются |
| POST | `/logout` | — | `204` |
| GET | `/me` | — | `{ user \| null }` |

Campus demo отвечает `403 CAMPUS_DEMO_DISABLED`, если выключен или процесс запущен в production; bootstrap не выполняется. При несовместимых связях зарегистрированного fixture — `409 CAMPUS_DEMO_COLLISION`, без захвата или исправления чужих записей. Обычный `/login` всегда отклоняет Campus registry-аккаунты, даже если их password hash был изменён локально. Восстановление отозванной административной роли не входит в повторный bootstrap: вход может завершиться успешно, а запрос кабинета без роли вернёт 403.

### Публикации `/api/opportunities`

| Метод | Путь | Описание |
|---|---|---|
| GET | `/?city=&kind=&q=&online=1&author=` | Список (`kind`: `meetup` · `job` · `idea` · `event`; `author=me` — свои) |
| GET | `/:id` | Одна публикация |
| POST 🔒 | `/` | Создать: `{ kind, title, description, city, roles[], direction?, stage?, online?, size?, deadline?, cover?, date?, time?, place?, coords?, campusId? }`. Заодно появляется в «Моих проектах» |
| DELETE 🔒 | `/:id` | Удалить свою |
| POST 🔒 | `/:id/apply` | Заявка `{ role, message, portfolio? }` → уходит автору в личный чат, ответ `{ application, conversationId }` |
| DELETE 🔒 | `/:id/apply` | Отозвать заявку |
| PUT / DELETE 🔒 | `/:id/attend` | «Я пойду» / отменить |
| PUT / DELETE 🔒 | `/:id/save` | Сохранить / убрать из сохранённого |

Для `kind=event` обязательны `date` (существующая календарная дата `YYYY-MM-DD`), `time` (`HH:mm–HH:mm`,
окончание позже начала), `place` (адрес/название площадки) и `coords: [latitude, longitude]` с валидными диапазонами.
Точка обязательна и при `online=true`. Эти значения сохраняются без подмены; `deadline` остаётся сроком набора,
а не датой события. Город должен входить в `CITY_COORDS`. У остальных видов публикаций точка без `coords`
пока приблизительная, в пределах выбранного города.

Для безопасного повтора `POST /api/opportunities` поддерживает необязательный заголовок **`Idempotency-Key`**: 1–128 печатных ASCII-символов без пробелов, например UUID. Ключ привязан к текущему пользователю и каноническому телу после серверной валидации, а не к порядку JSON-полей.

| Повтор | Результат |
|---|---|
| Тот же пользователь, ключ и валидное тело | `201 { item }` с исходным ID, без новой публикации, проекта, usage или расхода Campus; проверка повтора выполняется до нового тарифного gate |
| Тот же пользователь и ключ, другое валидное тело | `409 IDEMPOTENCY_CONFLICT`, без изменений |
| Публикация по сохранённому ключу уже удалена | `410 IDEMPOTENCY_GONE`, повтор её не воссоздаёт |
| Другой пользователь с таким же ключом | Отдельная операция этого пользователя |
| Ошибка валидации или `402 PAYMENT_REQUIRED` | Ключ не резервируется, можно повторить после исправления данных/изменения покрытия |

Ключ успешной операции сохраняется после удаления публикации и не истекает автоматически. Клиенты без заголовка совместимы, но повтор после потерянного ответа для них не защищён от создания отдельной публикации.

Совместимость после восстановления тарифов: новые ключи пишутся в нейтральную `publication_requests` с `hash_version='v2'`. Добавленная колонка помечает прежние строки как `neutral`. При повторе сервер под одной блокировкой `BEGIN IMMEDIATE` читает эту таблицу и прежнюю `billing_publication_requests` до тарифной проверки и привязки Campus. Прежние ключи не переносятся и не перезаписываются; несовместимые результаты/тела для одного ключа в двух таблицах дают 409. Только для старой строки `neutral`, когда выпуск без тарифов игнорировал переданный `campusId`, повтор возвращает прежнюю личную публикацию без новой привязки к вузу. Новые ключи строго учитывают добавление, удаление и смену `campusId`. Уже удалённый результат остаётся 410. Такая совместимость не требует reset, повторного seed или назначения администраторов.

При старте личные публикации этого промежуточного выпуска и tombstone-записи его удалённых результатов получают один учёт `legacy` в исходном месяце `Asia/Almaty`, с нулевой ценой и без расхода Campus. Контент, статусы модерации, права и прежние записи использования не переписываются. В режиме `preview` этот учёт не ограничивает бесплатное создание.

### Цены и учёт `/api/billing`

Интерфейсы тарифов и Campus восстановлены для desktop web. Мобильная версия из исходного архива не показывает эти разделы. API не определяет права по ширине экрана: сохранённые серверные роли и проверки остаются действующими.

Платёжного провайдера, checkout, списаний с карты и регулярных платежей **нет**. По умолчанию работает `preview`: все публикации бесплатны, сервер лишь показывает расчёт будущего тарифа и учитывает использование. В `enforced` бесплатная/покрытая публикация разрешена; требующая платежа получает `402 { code: 'PAYMENT_REQUIRED', error, quote }` без создания публикации и расхода квоты. Этот режим не имитирует успешно проведённую оплату.

| Услуга (`service`) | Обычная цена, ₸ | Подтверждённый студент, ₸ |
|---|---|---|
| `publication` после первой бесплатной публикации месяца | 500 | 250 |
| `promotion3`, необязательное продвижение на 3 дня | 500 | 250 |
| `promotion7`, необязательное продвижение на 7 дней | 1 000 | 500 |

Это разовые услуги без автопродления. Продвижение считается отдельно от публикации. **Активации продвижения пока нет**: `promotionActivationAvailable: false`; запрос цены не поднимает публикацию, не запускает срок и не расходует кредит.

| Метод | Путь | Ответ / назначение |
|---|---|---|
| GET | `/plans` | Публичный каталог `{ mode, pilotFree, currency: 'KZT', timezone: 'Asia/Almaty', publication, promotion3, promotion7, campus, paymentAvailable: false }` |
| GET 🔒 | `/quote?service=publication` | Расчёт новой публикации для текущего пользователя |
| GET 🔒 | `/quote?service=promotion3&opportunityId=:id` | Расчёт продвижения; при указанном ID проверяется право владельца. `promotion7` — аналогично |
| GET 🔒 | `/me` | `{ mode, pilotFree, period, studentVerified, usedPublications, freeRemaining, campus: [{ service, remaining, expiresAt }] }` |

Для продвижения `opportunityId` обязателен: без него — `400 OPPORTUNITY_REQUIRED`, для чужой публикации — `403 NOT_OWNER`, для отсутствующей — `404 OPPORTUNITY_NOT_FOUND`. Неподдерживаемый `service` отклоняется. Запросы `/quote` и `/me` ничего не резервируют и не расходуют.

Поля ответа `/quote`:

| Поле | Значение |
|---|---|
| `service`, `currency`, `mode`, `pilotFree`, `period` | Услуга, KZT, режим и серверный месяц `YYYY-MM` |
| `studentVerified`, `unitPrice` | Проверенный сервером студенческий статус и цена услуги по этому статусу |
| `expectedAmount`, `expectedSource` | Сумма/основание по тарифу: `monthly_free`, затем `campus`, иначе `payment_required` |
| `amountDue`, `source` | Фактические условия текущего режима; для публикации в пилоте всегда `0` и `pilot`. Для продвижения это только расчёт без доступной активации |
| `usedPublications`, `freeRemaining` | Сколько успешных публикаций учтено в месяце и остаток бесплатной квоты |
| `campusCovered` | Campus выбрано как основание расчёта этой услуги; при приоритетной месячной квоте — `false` |
| `paymentRequired`, `canPublish` | Требуется ли платёж в текущем режиме и разрешена ли публикация |
| `promotionActivationAvailable` | Всегда `false` в текущей версии |

У `/plans` поле `pilotFree` описывает режим публикаций в целом, а у `/quote` — конкретную услугу. В `preview` для продвижения `pilotFree=false`: возвращается справочная цена/покрытие, но активации и оплаты всё равно нет.

Первая публикация пользователя в календарном месяце бесплатна для любого вида публикации. Месяц вычисляется по **Asia/Almaty** на сервере. Например, `2026-10-31T18:59:59.999Z` ещё относится к октябрю, а `2026-10-31T19:00:00.000Z` — уже к ноябрю. Часовой пояс браузера и переданные клиентом время/цены на расчёт не влияют.

Успешная публикация и запись использования выполняются атомарно после проверки данных. Удаление публикации не удаляет историю использования и не возвращает бесплатный слот. Существующие публикации с автором учитываются начальным заполнением истории (`legacy`), чтобы обновление приложения не обнуляло квоту текущего месяца. Ошибочная форма и отклонённая публикация использование не увеличивают. Quote — снимок условий: финальная транзакция проверяет их заново.

Студенческое подтверждение выдаётся доверенной стороной на сервере — локальным администратором или администратором своего Campus после рассмотрения заявки. Поля профиля, email и клиентские флаги прав не дают. Глобальное подтверждение локального администратора и подтверждение членства конкретного Campus учитываются независимо: отзыв вузом своего подтверждения не удаляет глобальную запись. Доступен кабинет Campus для рассмотрения заявок, модерации добровольно привязанных публикаций и выдачи/отзыва кредитов. Автоматической проверки документов, платёжного портала и приёма оплаты от вуза нет; цена Campus пока `null`. В расчёте первой публикации приоритет у месячной бесплатной квоты, затем у действующего остатка Campus по конкретной услуге: студент не должен повторно платить за покрытую услугу или расходовать оба основания сразу.

В бесплатном пилоте публикация увеличивает месячный счётчик, но не расходует Campus: фактическое основание — `pilot`, даже если `expectedSource='campus'`. В `enforced` расходуется только действующий кредит выбранной услуги; среди подходящих кредитов первым используется истекающий раньше. Выдача кредита другой услуги не даёт покрытия публикации.

До подключения настоящих платежей потребуются платёжный провайдер, подтверждение успешного платежа на сервере и полный жизненный цикл оплаты/возврата. Текущие ответы нельзя использовать как подтверждение получения денег.

Сценарии ручной проверки и ожидаемые инварианты перечислены в [docs/billing-qa.md](../docs/billing-qa.md). Автоматические тесты запускаются через `npm test` из корня; тесты сервера используют отдельную временную БД.

### Доверенное локальное управление студентами и Campus

Команды выполняет администратор с доступом к серверу и его БД. Они используют тот же `DB_PATH` из `backend/.env` и **изменяют действующие записи**; это не публичная регистрация и не подтверждение оплаты. Пользователь с переданным email должен быть уже зарегистрирован. Скрипты объявлены в `backend/package.json`, реализация — `src/billing-admin.ts`.

Из корня проекта подтвердить студента:

```bash
npm run billing:student -w backend -- --email student@example.kz --source university --verified-by "Учебный офис" --expires "2027-01-01T00:00:00+05:00"
```

`--source` обязателен: `admin` или `university`. `--verified-by` необязателен, по умолчанию `local-cli:<source>`. `--expires` необязателен: без него подтверждение бессрочно; при указании нужна будущая ISO-дата с часовым поясом. Повторная выдача обновляет запись пользователя, не создавая второй статус. Даты нормализуются в UTC.

Отозвать подтверждение:

```bash
npm run billing:student -w backend -- --email student@example.kz --revoke
```

Для отзыва используются только `--email` и `--revoke`; поля выдачи вместе с ними отклоняются.

Выдать кредит Campus на конкретную услугу:

```bash
npm run billing:grant -w backend -- --email student@example.kz --service publication --quota 2 --expires "2027-01-01T00:00:00+05:00" --campus "Название университета"
```

`--service` — `publication`, `promotion3` или `promotion7`; `--quota` — целое от 1 до 100 000. `--expires` и `--campus` обязательны. Необязательный `--starts` задаёт ISO-момент начала с часовым поясом, по умолчанию кредит действует с момента команды. Окончание должно быть в будущем и позже начала. Каждая команда выдачи создаёт отдельный кредит; команда не означает банковского платежа или работающей активации продвижения. В примерах замени email на существующий и срок — на подходящий будущий.

Здесь `billing:grant --campus` — текстовая отметка выдавшей стороны, а не ID/права кабинета. Такие локальные кредиты не становятся управляемыми администратором вуза по совпадению названия. Для кредита, связанного с конкретным Campus и его действующим студентом, используется защищённый API кабинета ниже.

### Campus `/api/campus` 🔒

Все методы требуют сессию. `/me` показывает данные текущего пользователя; `/enroll` создаёт только его собственную заявку. Для остальных путей нужна отдельная серверная роль администратора **того Campus, который указан в URL**. Профессия `users.role`, студенческий статус, известный ID и клиентские флаги её не заменяют.

Объект Campus содержит `{ id, name, city }` и дополнительное `isDemo: true` для зарегистрированной демонстрации. `/me` фильтрует `adminOf`, `membership` и `available` по допустимому типу tenant. Реальному пользователю запрещён enrollment в демо-Campus, даже если ID известен; демонстрационному — в настоящий.

| Метод | Путь | Тело / результат |
|---|---|---|
| GET | `/me` | `{ adminOf: [{ id, name, city }], membership: null \| { campus, userId, status, faculty, studyYear, requestedAt, verifiedAt, expiresAt, current }, available: [{ id, name, city }] }` |
| POST | `/enroll` | `{ campusId, faculty, studyYear }` → `201 { membership }` со статусом `pending`; `studyYear` — целое 1–8 |
| GET | `/:campusId/overview?days=30` | Реальные агрегаты своего Campus; `days` — 7, 30 или 90, по умолчанию 30 |
| GET | `/:campusId/students?status=all&q=&page=1` | `{ items, total, page, pageSize: 20 }`; статус `all/pending/verified/rejected/revoked`, поиск по имени/email/факультету только внутри Campus |
| PATCH | `/:campusId/students/:userId` | `{ status: 'verified' \| 'rejected' \| 'revoked', expiresAt?: ISO \| null }` → `{ student }`; ненулевой срок должен быть в будущем |
| GET | `/:campusId/publications?status=all&q=&page=1` | `{ items, total, page, pageSize: 20 }`; `status` — `all/visible/hidden`, только явно привязанные публикации этого Campus |
| PATCH | `/:campusId/publications/:id` | `{ hidden, reason }` → `{ item }`; для скрытия причина 3–500 символов, для восстановления допустима пустая строка |
| GET | `/:campusId/grants?page=1` | `{ items, total, page, pageSize: 20 }`; квота, использование, остаток, сроки, отзыв и `active` каждого кредита |
| POST | `/:campusId/grants` | `{ userId, service, quota, expiresAt }` и обязательный `Idempotency-Key` → `201 { grant }`; только действующий подтверждённый студент этого Campus |
| POST | `/:campusId/grants/:id/revoke` | `{ grant }`; отзыв сохраняет историю и прежнее использование, повтор не расходует ресурсы |

У пользователя одна запись заявки/членства Campus. При действующем подтверждении новая заявка отклоняется с `409 MEMBERSHIP_EXISTS`, не меняя статус. После отказа, отзыва или истечения срока можно подать заявку заново, в том числе в другой Campus: она снова требует рассмотрения. Самостоятельно передать `verified`, чужой `userId` или роль администратора нельзя. Сохранённый `status='verified'` с истекшим сроком имеет `current=false`; фильтр по сохранённому статусу и счётчик действующих подтверждений — разные величины.

Веб-кредит действует с момента выдачи, имеет целую квоту 1–100 000 и будущий `expiresAt` в ISO с зоной; дата нормализуется в UTC. `Idempotency-Key` — 1–128 печатных ASCII-символов без пробелов, область ключа — Campus. Повтор того же валидированного тела возвращает прежний кредит без второй выдачи/записи аудита, другое тело с тем же ключом — 409. Повтор возвращает прежний кредит и после отзыва; он не делает его снова активным. Другой вуз не может увидеть или отозвать кредит по известному ID. Отказ/отзыв членства отзывает кредиты именно этого Campus; истёкшее/неподтверждённое членство также исключает их из расчёта. Глобальные локальные кредиты и другая область выдачи этим не изменяются.

При создании публикации `campusId` — **добровольная привязка**, проверяемая внутри общей транзакции создания/биллинга. Нужен действующий подтверждённый студент именно этого Campus. Одна роль администратора Campus не даёт студенческую скидку или право публиковаться от вуза. Без `campusId` публикация остаётся личной: вуз не получает доступ к ней для модерации, даже если автор учится в нём. Старые личные публикации автоматически не импортируются.

Скрытие Campus-публикации обратимо и убирает её из публичного списка/карты и чужого профиля; прямое публичное чтение, новые отклики, «Я пойду» и сохранение тоже закрыты. Автор в своём профиле и администратор этого Campus сохраняют доступ к карточке и причине. Другой вуз не может скрыть личную или чужую Campus-публикацию. Скрытие не удаляет публикацию, usage, существующие переписки или историю модерации; удаление автором по-прежнему не возвращает бесплатную квоту.

`overview` возвращает `{ campus, days, from, through, counts, daily, byKind, recentActivity }`. Дни рассчитываются в `Asia/Almaty`. Определения:

- `counts.publications`, `hiddenPublications`, `applications`, `daily`, `byKind` — сохранённые публикации, явно привязанные к этому Campus, и заявки на них за выбранные календарные дни. Личные публикации не входят.
- `studentsTotal`, `pendingStudents`, `verifiedStudents` — текущее состояние записей Campus; `verifiedStudents` учитывает только действующие подтверждения.
- `activeStudents` — число разных пользователей из текущей таблицы студентов этого Campus, которые в периоде создали его публикацию либо оставили заявку на его публикацию. Здесь учитываются все сохранённые статусы членства, а не только `verified`.
- `attendancesTotal` — текущие отметки участия в событиях Campus **за всё время**, поскольку у отметки нет времени создания. Это отдельная величина от периода графика.
- `recentActivity` — последние 20 записей аудита Campus **за всё время**. Это технические действия с непрозрачными ID и временем; в аудит не копируются сообщения, свободный текст профиля и причины модерации.

Просмотров, охватов, вымышленных посещений и статистики личных чатов нет. Агрегаты строятся по текущим сохранённым строкам: удаление публикации или отзыв заявки может изменить результаты за прошлый период; это не неизменяемый снимок исторической аналитики.

### Создание Campus и назначение администраторов

Назначение полномочий доступно только доверенному локальному CLI с доступом к серверной БД. Веб-администратор вуза не может назначить себя в другой вуз или выдать эту роль студенту через HTTP.

Из корня проекта:

```bash
npm run campus:create -w backend -- --name "Евразийский университет" --city "Астана" --admin-email admin@example.kz
npm run campus:admin -w backend -- --campus campus_ID --email admin@example.kz --grant
npm run campus:admin -w backend -- --campus campus_ID --email admin@example.kz --revoke
```

В ответе создания возвращается `{ campus, admin }`; используй реальный `campus.id` вместо `campus_ID` и существующий зарегистрированный email. `--admin-email` необязателен: без него создаётся Campus без администраторов (`admin: null`), никаких полномочий автоматически не выдаётся. В `campus:admin` назначение — действие по умолчанию, `--grant` — явный вариант; `--grant` и `--revoke` одновременно запрещены. Повтор назначения/отзыва не дублирует полномочия и записи аудита.

CLI не смешивает настоящие аккаунты и демонстрационные Campus-роли: выдать реальному пользователю роль в демо или registry-пользователю роль настоящего вуза нельзя. Отзыв остаётся доступен; повторный demo bootstrap отозванную роль не восстанавливает.

Создание Campus, назначение администратора и выдача кредитов не проводят платёж. Бесплатный пилот `BILLING_MODE=preview` остаётся включённым по умолчанию. Цена коммерческого пакета пока не установлена, продвижение не активируется. Сценарии изоляции и проверки кабинета — в [docs/campus-qa.md](../docs/campus-qa.md).
