# Проверка кабинета Campus

Проверять на отдельной временной БД. Кабинет работает; платежей и активации продвижения нет. Основной пилот `BILLING_MODE=preview` по-прежнему делает все публикации бесплатными. Для проверки расхода Campus можно отдельно использовать `enforced`: это проверка квоты/покрытия, а не настоящее списание денег.

Кабинет восстановлен в desktop web; мобильная версия из исходного архива не показывает Campus и тарифы. Восстановление API использует прежние строки Campus и администраторов без reset, seed или автоматической выдачи новых ролей. При наличии такой истории `npm run seed` отказывает; рабочую БД не удалять.

## Подготовка

1. Зарегистрировать администратора A, администратора B, студентов S1/S2 и обычного пользователя V. Роли в профессии профиля не менять как способ авторизации: они прав не дают.
2. Доверенным локальным `campus:create` создать Campus A и B, назначив соответствующих существующих администраторов. Можно использовать одинаковые названия вузов: область доступа определяется ID, а не текстовым названием.
3. S1 подаёт собственную заявку в A, S2 — в B. Подтвердить каждую из соответствующего кабинета с будущим сроком.
4. Создать P1 с явным `campusId=A`, P2 с `campusId=B` и личную публикацию L1 студента S1 без `campusId`.

Полный синтаксис CLI и API — в [backend/README.md](../backend/README.md). Демо-сид не назначает роли вуза автоматически. Отдельный явный вход в «ЕНУ · демо» имеет собственные проверки в [demo-qa.md](./demo-qa.md); он не заменяет двух независимых вузов для проверки tenant isolation ниже.

## Роли и изоляция

| Действие | Ожидаемый результат |
|---|---|
| Гость вызывает `/api/campus/me`, `/enroll` или административный путь | 401, никакие данные или изменения не выдаются |
| V/S1 меняет профессию на `admin`, передаёт административные флаги или открывает известный `/campus/A` | Не получает полномочия; административный API возвращает 403 |
| Администратор A запрашивает обзор, студентов, публикации или кредиты B | 403, без данных другого вуза; неизвестный Campus не становится способом перечисления привилегированных сущностей |
| Администратор A передаёт ID студента/публикации/кредита B в путь A | 404 внутри своей области или отказ до изменения; данные B, его аудит, остатки и статусы не меняются |
| Администратор только с ролью вуза запрашивает студенческую цену или создаёт Campus-публикацию без отдельного подтверждения | Административная роль не выдаёт скидку или право привязки; студенческий тариф/публикация требуют собственного действующего подтверждения |
| Через CLI отозвана роль A, но его браузер ещё открыт | Следующие защищённые запросы получают 403; UI очищает привилегированные данные после отказа и не продолжает изменения по старому кешу |
| Смена аккаунта либо переключение A → B во время запроса | Старый ответ не заполняет чужой кабинет; роль, поисковая выдача, выбранный студент и незавершённая выдача не переносятся между областями |

## Своя заявка и подтверждение

- POST `/enroll` с факультетом/курсом создаёт только собственную `pending`-заявку. Передача чужого `userId`, `verified` или роли отклоняется строгой схемой; отправка заявки не даёт скидку, кредит или право публиковаться от Campus.
- Только администратор A может подтвердить S1 в A. Установить будущий срок, проверить `current=true`, студенческий тариф и доступную привязку публикации.
- Новая собственная заявка при действующем подтверждении получает `409 MEMBERSHIP_EXISTS` и не понижает статус до `pending`.
- Отказ, отзыв и истечение срока дают `current=false`. Сохранённый статус может оставаться `verified` после истечения; UI должен явно показывать недействующее подтверждение. Повторная заявка снова `pending` и требует новой проверки.
- После окончания/отзыва A студент может подать заявку в B. Попытка A затем изменить запись уже принадлежащую B не меняет B. Независимая глобальная верификация локального администратора не удаляется вузовским действием.
- Некорректный курс (нецелый, вне 1–8), пустой факультет и неверный/прошедший срок не дают частичного изменения или записи успеха.

## Только добровольные публикации

1. Убедиться, что A видит P1, B — P2; ни один кабинет не импортирует личную L1 просто по автору, городу или студенческому статусу.
2. S1 не может создать публикацию с `campusId=B`. После отзыва/истечения его подтверждения A новая привязка к A тоже отклоняется; публикация, проект, usage и аудит не остаются частично созданными.
3. Автор добровольно привязывает публикацию при создании; явный `campusId` входит в идентичность идемпотентного запроса. Повтор успешного создания после последующего отзыва членства возвращает прежнюю публикацию и не создаёт новую привязку/usage.
4. Скрыть P1 из A с причиной минимум 3 символа. После обновления публичных запросов P1 отсутствует в списке/карте и чужом профиле. Прямой GET и новые отклик/участие/сохранение пользователем V получают 404.
5. Автор через собственный профиль и администратор A сохраняют доступ к P1 и причине. Другой вуз и обычный посетитель не получают приватную причину модерации. Личные переписки и существующая история не удаляются.
6. Восстановить P1: она снова публична. Повторить попытку скрыть L1 или P2 путём A — отказ без изменений. Скрытие не удаляет usage и не возвращает бесплатную квоту/Campus; удаление автором также не возвращает расход.

## Кредиты Campus и безопасный повтор

| Сценарий | Ожидаемый результат |
|---|---|
| Выдать кредит S1 в A | Только действующему подтверждённому S1; будущий срок, конкретная услуга и целая квота 1–100 000 обязательны |
| Попытка выдать кредит pending/expired/revoked S1 или S2 из B | Отказ; не появляется кредит, запросный ключ или запись успешной выдачи |
| Один и тот же `Idempotency-Key` и валидированное тело отправлены повторно | Тот же кредит, один остаток и одна запись аудита. Ключ действует внутри Campus; другой вуз не получает прежний результат |
| Тот же ключ с другим телом | 409, без второй выдачи и изменения исходной |
| Первый ответ потерян; обновить страницу и повторить из сохранённой формы | Сохранённый ключ и точное тело восстанавливаются из `qadam.campus.grant.<adminUserId>.<campusId>`; форма не выдаёт другой пакет во время неопределённого исхода |
| Кредит после первого успеха уже отозван/истёк, затем повторён прежний ключ | Возвращается исходный кредит с текущим неактивным состоянием, без повторного включения. UI не обещает действующее покрытие вопреки истории |
| Выбрать студента и заполнить квоту/срок, затем листать поиск получателей или нажать Enter в поиске | Пагинация и поиск не отправляют форму и не выдают пакет прежнему выбранному студенту; выдача требует явного действия |
| Браузер не позволяет сохранить безопасную попытку | Новая выдача не отправляется небезопасно; доступна понятная ошибка. При неизвестном результате поля не разблокируются для создания дубля |
| Отозвать кредит A по его ID и повторить отзыв | Остаток A становится недоступен, прежнее usage сохраняется; повтор не дублирует расход или аудит |
| Отказать/отозвать членство S1 в A | Кредиты A отозваны/неактивны, данные и usage сохранены. Глобальные локальные кредиты и подтверждение не удаляются; грант B по известному ID нельзя затронуть из A |

В `preview` публикация увеличивает месячный счётчик, но не расходует кредит Campus. В `enforced` сначала используется первая бесплатная публикация месяца, затем подходящий кредит. Одно создание не расходует оба основания. Кредит на продвижение не даёт покрытия публикации и не включает продвижение, которого пока нет.

## Реальные определения статистики

На пустом Campus все метрики равны нулю; график всё равно содержит 7/30/90 календарных дней без выдуманных событий. Сверить показатели со своими данными в БД:

- Публикации/скрытые публикации за период и распределение по типам — только явно привязанные к выбранному Campus. Личная L1 и P2 другого вуза не входят в A.
- Отклики и дневной график — реальные сохранённые заявки на публикации выбранного Campus. Личные сообщения, просмотры и неподтверждённые «охваты» не создают активности.
- `activeStudents` — разные ID из текущих записей студентов этого Campus, которые создали его публикацию или оставили заявку на его публикацию в периоде. Статусы здесь любые; это не счётчик только действующих `verified`.
- Текущие студенты, pending и действующие verified показываются отдельно от диапазона графика.
- «Я пойду» — текущее количество отметок **за всё время**, а не за 7/30/90 дней; у записи нет времени создания.
- Журнал — последние 20 действий Campus **за всё время**. Повтор идемпотентной выдачи/отзыва не добавляет вымышленное второе действие. В журнал не копируются имена/email, тексты переписок, биография или причина модерации.
- Дни и границы периода — `Asia/Almaty`; смена часового пояса браузера не меняет серверный диапазон. Удалённая публикация/отозванная заявка могут изменить счётчики: это агрегаты текущих данных, а не неизменяемый исторический отчёт.

## Пользовательские сценарии

На телефоне и компьютере проверить вход с возвратом на `/campus/:id?tab=grants`, переключение вуза и вкладок, поиск/страницы, подтверждение/отзыв, видимую ошибку и повтор после потери сети. Никакая загрузка, повтор GET, пагинация или выбор вкладки не создают кредит и не меняют статус. Кабинет работает без платёжного провайдера, а выдача покрытия не выдаётся за доказанный банковский платёж. Создание вуза и назначение роли возможны только доверенным локальным CLI, не обычным профилем или HTTP-флагом.
