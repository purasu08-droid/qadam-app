# Проверка демо-входов и «ЕНУ · демо»

Проверять на отдельной временной SQLite через `DB_PATH`, не на рабочей базе пользователя. Не запускать `npm run seed` для восстановления демонстрации: защищённая история блокирует reset, а незащищённая тестовая БД пересоздаётся. Демо Campus — общий аккаунт и отдельный tenant; действия других посетителей демонстрации могут быть видны после обновления. Это не отдельная копия всей платформы на каждый вход: изоляция относится к кабинету Campus, общие функции QADAM остаются в том же приложении.

Сценарии интерфейса Campus demo относятся к desktop web. Мобильная версия из исходного архива не показывает Campus/тарифы и использует прежний мобильный вход. После восстановления API уже сохранённый demo registry работает по тем же настройкам среды, не сбрасывая fixture и отозванные полномочия.

## Доступность и старые сессии

Для смены окружения перезапускать API, сохраняя ту же временную БД и cookie jar. Проверять реальные endpoints, а не только наличие кнопки. Запрет production без override относится к Campus demo; обычный seed demo сохраняет прежнюю настройку.

| Окружение | Ожидание |
|---|---|
| Dev, `ALLOW_DEMO_LOGIN` не задан | Campus demo разрешено; обычный demo доступен только при наличии seed-аккаунта; `GET /api/auth/options` сообщает эти возможности |
| Dev, `ALLOW_DEMO_LOGIN=false` | Варианты выключены, оба POST возвращают 403 до bootstrap/выдачи сессии |
| Production, значение не задано | Оба варианта запрещены |
| Production, `ALLOW_DEMO_LOGIN=true` | Campus demo запрещено; обычный seed demo разрешён при наличии аккаунта |
| Успешная Campus demo-cookie, затем restart с `false` или production | `/api/auth/me` не возвращает registry-пользователя; защищённые Campus API с той же cookie отвечают 401 |
| Уже выданная cookie обычного seed-аккаунта, затем выключение демо | Не путать с Campus registry: эта сессия не отзывается автоматически данным флагом |
| Настоящий пользователь с действующей cookie, затем выключение демо | Его сессия остаётся доступна; запрет демо не является общим выходом всех пользователей |

`SEED_DEMO_DATA` проверять отдельно: production выключает автосид по умолчанию, но явный `true` остаётся настройкой автозаполнения пустой БД. Он не разрешает Campus demo и не меняет `BILLING_MODE=preview`. На пустой БД с `SEED_DEMO_DATA=false` options сообщает `demoLogin=false`, `campusDemoLogin=true` при разрешённом dev-демо; прямой обычный `/demo` даёт 503 без совета удалить данные/запустить reset, а Campus demo выполняет собственный bootstrap.

Проверить прямой POST при устаревшем успешном `/options`: сервер повторно применяет запрет. Ошибка сети при загрузке `/options` не должна показывать разрешённые демо-действия; доступна повторная попытка, обычный вход/регистрация не зависят от загрузки демо-условий.

## Fixture, повтор и конфликты существующих записей

1. На пустой временной БД вызвать `POST /api/auth/campus-demo`. Ответ открывает отдельный «ЕНУ · демо» и выдаёт cookie демонстрационного администратора. Реальный Campus с названием ЕНУ, если он существует, остаётся отдельным ID без новых администраторов.
2. Проверить обзор/студентов/публикации/пакеты: данные относятся к демо-Campus. Персональные публикации существующих пользователей и записи другого Campus не становятся демонстрационными автоматически.
3. В демонстрации рассмотреть заявку, скрыть публикацию с причиной, выдать/отозвать пакет. Повторить вход и обновить страницу: ID fixture, результаты действий, аудит и остатки сохраняются; bootstrap не восстанавливает исходный статус/видимость/квоту и не добавляет дубли.
4. Повторить два одновременных bootstrap на одной БД: один fixture, без частично выданных ролей и дублирующих студентов/публикаций/пакетов.
5. На отдельных временных БД смоделировать конфликт служебного реестра с реальным Campus или чужого автора/tenant у зарегистрированного объекта: 409 `CAMPUS_DEMO_COLLISION`, чужие записи не исправляются и права не выдаются. При искусственном конфликте INSERT посередине нового bootstrap вся транзакция откатывается без частичных fixture/ролей/usage. Отдельно проверить существующий похожий email и Campus с названием «ЕНУ · демо»: новый fixture использует случайные ID/токены, эти настоящие записи не захватываются и не меняются.
6. Удаление/повреждение части служебных связей fixture не должно приводить к захвату чужой записи. Если восстановление невозможно без подтверждения владения, ожидается отказ, а не пересоздание через чужой ID/email.
7. Отозвать роль демо-администратора доверенной локальной командой и повторить вход: bootstrap не выдаёт её заново. Ответ входа может быть 200, но кабинет остаётся недоступен с 403. Удалённая демонстрационная публикация также не воссоздаётся.

У демо-администратора нет публичного пароля для обычного `/login`; новый fixture использует непригодное для парольного входа случайное значение. Проверить публичный seed-пароль и пустой пароль: не дают войти в него. Registry-аккаунт не должен обходить выключение демо обычным password login. Публичные seed-учётные данные обычной демонстрации также не должны работать после выключения демо. Изменённый пароль настоящего аккаунта с совпавшим seed email — отдельный случай, не основание для выдачи Campus-роли.

## Изоляция и данные

- Войти демо-администратором, обратиться ко всем административным endpoints другого Campus по известному ID: 403, без чужих студентов/пакетов/аудита и изменений. Подстановка чужого student/publication/grant ID в путь демо-Campus не меняет чужой объект.
- Обычный пользователь не получает роль, указав профессию администратора, название/ID демо-Campus или похожий email. Самостоятельная заявка в обычный вуз создаёт только `pending`.
- **Обязательный regression:** настоящим студентом получить `/api/campus/me`: демо-Campus отсутствует в `available`. Затем напрямую передать его известный ID в `/api/campus/enroll` — 403; существующая membership, статус, факультет/курс, кредиты и аудит не меняются, новая заявка не появляется. Повторить для пользователя без принадлежности и с pending/verified принадлежностью настоящего вуза.
- Настоящий администратор другого Campus не получает доступа к демо-Campus; локальный CLI также отклоняет смешивание настоящих пользователей и демо-ролей в обе стороны. Демонстрационный вход не назначает текущему реальному пользователю новую роль: он переключает сессию на отдельный демонстрационный аккаунт.
- Статистика считает фактические демонстрационные записи; нет выдуманных просмотров, чатов, оплаты или активации продвижения. Общий пилот остаётся бесплатным, а выдача кредита не подтверждает платёж университета.

## Маршрут, загрузка и смена сессии

| Сценарий в браузере | Ожидаемый результат |
|---|---|
| Campus demo с `/signin`, `/pricing` и гостевой страницы Campus | После ответа открывается именно серверный маршрут демонстрационного Campus, без промежуточного перехода на старый `from` |
| `/signin` имеет `from=/create?kind=idea#preview`, выбран Campus demo | Открывается демо-Campus; старый `from` не перехватывает специальное назначение |
| Обычный demo или email login с тем же `from` | Возвращается безопасный внутренний адрес вместе с query/hash |
| Внешний, protocol-relative, закодированный опасный `from` или `/signin` | Не используется как адрес возврата |
| Двойной клик, Enter, параллельный обычный login/demo/logout | Одна текущая запись сессии; кнопки отражают занятость, не отправляются конкурирующие переключения |
| Медленный Campus demo, переход на другую страницу/новая авторизация/выход | Устаревший результат не меняет новый аккаунт, кабинет или адрес назначения; старые приватные ответы не показываются в новой сессии |
| Bootstrap или POST завершился ошибкой/403/429 | Видимая ошибка и возможность повтора, без ложного сообщения об успешном входе; ожидающий интерфейс снимается |
| Обновление страницы после входа | Проверяется cookie; открытый кабинет остаётся доступен только при фактической роли и разрешённом сервером демо |

Проверки Campus дополняются [campus-qa.md](./campus-qa.md), цены и replay публикаций — [billing-qa.md](./billing-qa.md). Успешные unit/integration tests не заменяют проверку маршрута и состояний загрузки в браузере.
